# Smash Remix: stages and the moveset/action framework

How Remix 2.0.1 adds stages (the `add_stage` macro and the tables it fills) and how it extends the fighter action and moveset system, read from
the assembly source in `.toolchain/pkgs/smashremix-src` (bass; paths below are relative to its `src/`). The port reads the stage tables from the
Remix RAM image in `decomp/src/gr/grremix/grremixstage.c`; the hazards are in `docs/remix/hazards.md`, the vanilla patches in
`docs/remix/vanilla_patches.md`, the per-scope port map in `docs/remix/patch_audit_scopes.md`. Test: `SSB64_VS_STAGE=<decimal id>` with
`.claude/skills/remix-smoke-tests/scripts/stage_sweep.sh`, and `stage_select_sweep.sh` for the stage select.

## 1. Stages

### 1.1 How a stage is added

Every new stage is one call of `add_stage(name, display_name, bgm, bgm_occasional, bgm_rare, bgm_rare2, tournament_legal, tournament_hazard_mode,
netplay_legal, can_toggle, class, btx_word_1, btx_word_2, btx_word_3, variant_for_stage_id, variant_type, cloaking_device_rate,
super_mushroom_rate, poison_mushroom_rate, blue_shell_rate, lightning_rate, deku_nut_rate, franklin_badge_rate, series_logo, hazard_type, order)`
(`Stages.asm:4777`). There are 175 calls (`Stages.asm:5054-5285`, BTT and BTP included).

- `new_stages` (`Stages.asm:4695`) increments per call and the id is `0x28 + new_stages` (`Stages.asm:4780`), so the new ids are 0x29
  (`DEKU_TREE`) to 0xD7 (`HTP_FALL`), 175 of them.
- The macro writes `class_table`, `bonus_pointer_table`, `string_table`, `alternate_music_table`, `variant_table`, the custom item spawn rates,
  `series_logo_table`, `tournament_hazard_mode_table` and `stage_hazard_table` at offsets derived from the id (`Stages.asm:4800-4850`).
- Default music: `set_default_music` writes `track + 1` into `default_music_track_table` (`Stages.asm:4688`).
- Preview position: `add_position_array(stage, x, y, z)` (`Stages.asm:4858`). Background animation: `add_bg_animation` (`Stages.asm:4996`) and
  `set_bg_type` (`Stages.asm:5018`).
- The order in the settings lists comes from the `order` argument: after the calls, `sorted_stage_N` sorts the custom ids by `order`
  (`Stages.asm:5288+`).
- Per-stage data files live in `stages/*.asm` and `*.bin` (56 files), for example `stages/edo.asm` inserts `sprite_data` and defines
  `NUM_SPRITE_INFO_ARRAYS` and `STAGE_FILE_OFFSET` (`stages/edo.asm:2-5`); they are included inside `bg_info` (`Stages.asm:4891-4995`).

There is no per-stage table block: everything is a set of global tables indexed by stage id and filled by the macros.

### 1.2 Ids (`Stages.asm:20-246`)

Vanilla: 0x00 (`PEACHS_CASTLE`) to 0x28 (`BTP_NESS`, last of `BTX`); the BTT and BTP stages are 0x11 to 0x28. New: 0x29 to 0xD7, for example
`DEKU_TREE` 0x29, `FIRST_DESTINATION` 0x2A, `BATTLEFIELD` 0x31, `DR_MARIO` 0x33, `DRAGONKING` 0x35, `FRAYS_STAGE` 0x37, `TOH` 0x38, `FOD` 0x39,
`MEMENTOS` 0x3B, `N64` 0x3E, `SMBO` 0x42, `BLUE` 0x48, `ONETT` 0x49, `FROSTY` 0x4B, `SMASHVILLE2` 0x4C, `GERUDO` 0x63, `DRACULAS_CASTLE` 0xB0,
`TWILIGHT_CITY` 0xBA, `REMIX_RTTF` 0xBD, `SCUTTLE_TOWN` 0xBF, `TIME_TWISTER` 0xD2, `HTP_FALL` 0xD7. `MAX_STAGE_ID` is 0xD7
(`Stages.asm:243`), `RANDOM` is 0xDE (`Stages.asm:246`). The port's gkind is the Remix id: `grremixids.h` (`nGRRemixStage_*`) is generated by
`tools/gen_remix_stage_ids.py` from `scope id`. The names and classes of all 175 stages are in the `add_stage` lines
(`grep -n '^\s*add_stage(' Stages.asm`).

Classes (`Stages.asm:516-523`): `BATTLE` 0, `RTTF` 1, `BTP` 2, `BTT` 3, `SSS_PREVIEW` 4 (the Time Twister stage-select preview).

### 1.5 File ids

Each stage uses three consecutive file ids: `HEADER`, `STG` (+1) and `BG` (+2). Example: `STG_BATTLEFIELD_HEADER` 0x871, `STG_BATTLEFIELD`
0x872, `STG_BATTLEFIELD_BG` 0x873; `STG_DEKU_HEADER` 0x874 to `STG_DEKU_BG` 0x876 (`File.asm:44-49`). `File.asm` has 313 `STG_*` constants. The
`header` scope (`Stages.asm:277-512`) holds the same ids (for example `header.DEKU_TREE` 0x874); the vanilla stages keep their unnamed ROM ids
(`header.PEACHS_CASTLE` 0x103). `File.STAGE_ICONS_2` (0x153E) is not used. The port keeps the Remix ids: `yamls/remix/reloc_misc.yml` lists them as
`file_<decimal id>` (0x871 is `file_2161`). More in `docs/remix/file_table_and_loader.md`.

## 2. Moveset and the action framework

### 2.1 Overview

Each character has an action parameter array, an action array and a moveset file.

- Action array (`Character.asm:388-430` read, `Character.asm:505-546` write): entries of 0x14 bytes, `dh (param_offset << 6) | staling`, then
  `dw main`, `dw interrupt/other`, `dw physics`, `dw collision`. The four `dw` are MIPS subroutines: the main (update), interrupt, physics
  and map collision routines of `ftmain`/`ftcommon`.
- Parameter array (`Character.asm:414-428`): entries of 0xC bytes, `dw animation`, `dw command offset`, `dw flags`; `-1` keeps the parent's value.
- Shared actions are 0x000 to 0x0DB (`Action.asm:4-~446`). Per-character actions start at 0xDC (for example `Action.MARIO` 0x0DC to 0x0E4,
  `Action.asm:685-720`) and every character has its own ids in that range.
- State dispatch: `Action.change(action_id, fsm)` (`Action.asm:2098`) calls `0x800E6F24`, `ftMainSetStatus`.

In the port the synthesized Remix fighters read these tables from the Remix RAM image (`REMIX_ACTION_ARRAY_TABLE`, `ftremixbind.c`,
`ftremixvanillaprocs.c`) and bind each action's routines to C functions through the `FTRemixProc` tables; see `docs/remix/fighters.md`.

### 2.2 How a character is defined

- `define_character(name, parent, file_1 ... file_9, attrib_offset, add_actions, bool_jab_3, bool_inhale_copy, btt, btp, remix_btt, remix_btp,
  sound_type, variant_type)` (`Character.asm:53`) copies the parent's parameter and action arrays (`OS.copy_segment`, `Character.asm:166-201`)
  and adds `add_actions` slots. The parent is read from the original ROM (`read32 ... "../roms/original.z64"`, `Character.asm:36-52`).
- Falco: `define_character(FALCO, FOX, ...)` (`Character.asm:3677`), `add_actions = 0`, so he reuses Fox's slots 0xE1 to 0xE8. Wolf:
  `define_character(WOLF, FOX, ...)` (`Character.asm:3729`), also `add_actions = 0`.
- Registration: `main.asm` (at the root of the Remix source) includes `src/Falco/Phantasm.asm` (line 150), `src/Falco/Falco.asm` (151),
  `src/Wolf/WolfSpecial.asm` (208) and `src/Wolf/Wolf.asm` (209).

### 2.3 How a fighter file extends its parent

Example `Falco/Falco.asm`:

- Moveset: `insert NAME, "moveset/X.bin"` (`Falco.asm:7-53`); the labels become available as parameters. `Moveset.GO_TO(X)` chains loops
  (`Falco.asm:7`).
- Action parameters: `Character.edit_action_parameters(FALCO, Action.X, anim, moveset, flags)` (`Falco.asm:56-~99`), with `anim = File.*` and
  `moveset` a `.bin` label.
- Subroutines: `Character.edit_action(FALCO, 0xE1, -1, 0x800D94C4, Phantasm.ground_subroutine_, -1, -1)` (`Falco.asm:101-102`): main, interrupt,
  physics, collision; `Phantasm.*` are MIPS routines in the Falco sources.
- Menu: `edit_menu_action_parameters` (`Falco.asm:~105-112`). Action strings: `table_patch_start(action_string, ...)` (`Falco.asm:236`).
- Hooks into vanilla code: `OS.patch_start` in `Falco.asm:244-338` and `Phantasm.asm:257-266` (for example `0xD66E0` to `0x8015BCA0`, Fox neutral
  special).

### 2.5 Custom commands (`command.asm`)

- Bytes 0xD0 to 0xFF are custom commands. `load_command_` (`command.asm:14`) reads the byte and jumps to `command_table[cmd - 0xD0]`
  (`command.asm:1051`): 0xD0 frame speed multiplier, 0xD1 armour, 0xD2 hitbox direction, 0xD3 translation multiplier, 0xD4 y velocity, 0xD5 fast
  fall, 0xD6 random SFX, 0xD7 kinetic state, 0xD8 hitbox FGM, 0xD9 env colour, 0xDA switch direction, 0xDB go to moveset file, 0xDC L voice SFX.
  0xDD to 0xFF are free (`OS.NULL`).
- `command_table_2` (`command.asm:1101`) is the variant used by `load_command_2_` (`command.asm:54`) for skipped commands (size 8). The hooks
  are at `command.asm:1152-1172`: `0x800E0388`, `0x800E0548`, `0x800E072C`.
- `change_action_` (`command.asm:93`) is hooked at `0x800E6F2C` (`command.asm:1168-1170`), inside `ftMainSetStatus`.
- Hitbox hooks: `end_hitbox_` (`command.asm:149`, 0x800E852C), `create_hitbox_` (`command.asm:189`, 0x800DF1F0), `texture_form_fix_`
  (`command.asm:231`, 0x800E962C).

The port decodes the commands in `ftremixcommand.c` (`ftRemixCommandRun`), called from the three `load_command_` hook sites of `ftmain.c`.

### 2.6 Projectiles, skeleton and spawn

- `Projectile.asm:9-34`: custom projectile ids start after `VANILLA_LAST_ID` 0x1F; each `add_projectile(NAME)` defines `id.NAME`. The 12 are
  0x20 `SONIC_SPRING`, `BANJO_EGG`, `GOEMON_RYO`, `SHEIK_NEEDLE`, `CONKER_NUT`, `LANKY_NUT`, `GOLDENGUN_BULLET`, `DEDEDE_WADDLEDOO_BEAM`, and the
  four hazard projectiles 0x28 `PIRATELAND_CANNONBALL`, 0x29 `METALLICMADNESS_BEELASER`, 0x2A `RAINBOWROAD_CHAINCHOMP`, 0x2B
  `CACODEMON_THUNDERBALL`.
