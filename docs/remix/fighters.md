# Smash Remix fighters: ids, tables and how the port registers them

Covers how Smash Remix 2.0.1 adds fighters (read from `src/Character.asm`) and how the port turns that into registry rows.
Code: roster data `port/remix/remix_roster_data.h` (generated by `tools/gen_remix_roster.py`), blob loader
`port/remix/remix_roster.cpp`, registry `port/fighter_registry.{h,cpp}`, synth `FTData` builder `decomp/src/ft/ftport.c`, per-fighter
Remix code `decomp/src/ft/ftremix/`.
Test: `tools/test_remix_blobs.py` (blob contract), and a VS match with chosen fighters:
`.claude/skills/remix-smoke-tests/scripts/vs.sh <fkind>,<fkind> <input> <name>` (`SSB64_VS_FKINDS`, the Remix id is the port fkind).
Audit ledger (every item closed): `docs/remix/patch_audit.md`, group g10 (Character tables).

## Scope, conventions and limits

- Remix root (`R`): `.toolchain/pkgs/smashremix-src` (commit `5e04fe7`, "Smash Remix 2.0.1"). Every `src/...:line` citation is relative to `R`.
- Decomp (`D`): `decomp/`. Citations `decomp/...` are relative to the repository root.
- ROM addresses (`origin` in bass) are file offsets of the US image (`baserom.us.z64`); RAM addresses are the bass `base`, or the second
  argument of `OS.patch_start(ROM, RAM)`.
- The RAM address of a table or routine that the Remix source defines as a label is in `build/remixasm/remix.sym`, made by
  `scripts/remix/assemble-remix.sh` (bass `-sym` output). The port reads those addresses through `port/remix/remix_symbols.h`
  (`REMIX_SYM_*`, generated by `tools/gen_remix_actions.py`). Addresses of the vanilla tables are the ones cited in the asm.
- The RAM-to-decomp-function mapping uses the `// 0x8XXXXXXX` comments before each function in `decomp/src`. In `0x8010xxxx` to
  `0x8013xxxx` the SSB64 overlays share addresses, so an address alone can name a function of another overlay; section 5 says which
  rows are ambiguous. `tools/audit_remix_patches.py` resolves overlays by matching function prologues in the vanilla ROM and is the
  reference for every patch, not only the fighter tables.

### 1.2 Added fighters (0x1B, 0x1D to 0x60)

Each full `define_character(name, parent, ...)` receives the next id: `constant id.{name}((STRUCT_TABLE_END - STRUCT_TABLE) / 0x4)`
(`src/Character.asm:79-80`). `STRUCT_TABLE_END` starts at `STRUCT_TABLE + 0x6C` (27 entries, `:19-20`) and each define adds a 4 byte entry
(`:217-220`), so the call order in the file decides the id. The Mario clone (`:3357-3362`) takes 0x1C, which is why FALCO is 0x1D and
not 0x1C. The `// 0xNN - NAME` comments of the file match this numbering (`src/Character.asm:3354-3815`).

Total: `NUM_CHARACTERS = NUM_VANILLA_CHARACTERS(27) + 2 + ADD_CHARACTERS(68) = 97` (0x61) (`src/Character.asm:15, 17, 27`). The 68 of
`ADD_CHARACTERS` are FALCO to NCRASH (0x1D to 0x60); RANDOM and the clone are the "+2".

## 2. Tables the Remix extends or relocates

Convention: the vanilla table is **copied** to a new location (`move_*`, `OS.copy_segment`) and filled up to `NUM_CHARACTERS`; new
entries are written by `add_to_table` / `table_patch_start`. The "new location" is a build label, resolved in `build/remixasm/remix.sym`.

Address rule used by the code: data pointers `ptr - 0x80084800` give the ROM offset (`src/Character.asm:38-47`). This holds for the
struct table (ROM `0x92610` = RAM `0x80116E10`, `src/Character.asm:19` and `decomp/src/ft/ftdata.c`). Other vanilla data tables follow
the same rule (`ROM + 0x80084800`).

## 3. How a new fighter is defined

### 3.1 Macro signature

`define_character(name, parent, file_1, ..., file_9, attrib_offset, add_actions, bool_jab_3, bool_inhale_copy, btt_stage_id, btp_stage_id,
remix_btt_stage_id, remix_btp_stage_id, sound_type, variant_type)` (`src/Character.asm:53`), 21 arguments. Each argument is commented
at `src/Character.asm:3651-3675`.

Real example (Falco, `src/Character.asm:3677`):

```
define_character(FALCO, FOX, File.FALCO_MAIN, 0x0D0, 0, File.FALCO_CHARACTER, 0x13A, 0x0D2, 0x15A, 0x0A1, 0x013C, 0x474, 0x0, OS.TRUE, OS.TRUE, Stages.id.BTT_FALCO, Stages.id.BTP_FALCO, Stages.id.BTT_FALCON, Stages.id.BTP_GND, sound_type.U, variant_type.NA)
```

### 3.2 Steps the macro runs

1. Rejects the fighter if `parent > 0xB` (`src/Character.asm:54-55`).
2. Reads from the vanilla ROM the parent's struct pointer, param array, menu array and action array (`:38-47`, `:56-70`).
3. Computes the param array size = parent size + `add_actions` (`:72-74`).
4. Defines the id (`:79-80`) and creates the file pointer table (`:92-97`).
5. Writes the 0x78 byte struct (`:105-184`) with the file ids (`:110-128`), the attribute offset (`:174-175`) and the array pointers.
6. Copies the parent's param array and fills up to `param_array_size` (`:188-194`).
7. Copies the parent's action array and fills `add_actions * 0x14` (`:196-203`).
8. Creates a menu array of 0xF entries copied from the parent (`:205-211`).
9. Registers the struct in `STRUCT_TABLE_END` and the action array in `ACTION_ARRAY_TABLE` (`:213-222`).
10. Fills the id-indexed tables by copying the parent's entry (`add_to_table`, `:225-346`). Special cases: jab 3 and rapid jab
    (`:225-245`, per-parent rule, for example `MARIO/LUIGI/LINK/CAPTAIN/NESS` for jab 3), special moves (`:247-256`), entry
    (`:258-261`), other (`:263-275`), menu (`:276-296`), gfx routine end (`:289-296`), projectile (`:297-300`), id overrides (`:301-305`),
    Kirby inhale (`:307-318`), BTT/BTP and Remix BTT/BTP (`:319-330`), sound type (`:331-335`), variant type (`:336-340`), shield
    (`:341-345`), polygon (`:346-355`).
11. Counts `NUM_POLYGONS` and `NUM_REMIX_FIGHTERS` (`:347-357`).

action/param arrays map by shape.

Binary entry formats (the ROM is big endian):
- Param array (0xC B): `animation`, `command`, `flags` (`src/Character.asm:388-407`, written at `:414-427`).
- Action array (0x14 B): `dh (param_offset << 6) | staling`, `dh unknown`, `dw asm1`, `dw asm2`, `dw asm3`, `dw asm4` (`src/Character.asm:505-536`, `:623-700`).
- Menu array (0xC B per entry, 0xF entries): `animation`, `command`, `flags` (`src/Character.asm:481-503`).

Actions: ids below 0xDC are shared. A fighter's own actions start at 0xDC: `Action.X = (action_array_size(parent) / 0x14) + n + 0xDC`
(`src/Character.asm:679-685`). New entries are created with `add_new_action` (`:623`), which consumes the `add_actions` slots declared
(`:554`, `:631` warn when slots run out).

## 4. Clone (parent) and shared code

### 4.1 Parent rule

- The parent must be a vanilla id `<= 0x0B` (`src/Character.asm:54-55`, `:366-367`). A Remix fighter cannot clone another Remix fighter directly.
- For polygons (N variants) the Remix uses `Character.polygon_setup(NAME, REMIX_PARENT)` (`src/Character.asm:2847-2910`), which copies the AI,
  the text action, the default costume and the music, and registers the id in `SinglePlayerModes.polygon_id_table`. Example:
  `src/NFalco/NFalco.asm:90` (`polygon_setup(NFALCO, FALCO)`), with declared parent `FOX` (`src/Character.asm:3793`).
- Every id table is filled by `add_to_table`, which copies the parent's entry (`src/Character.asm:842-845`). A clone therefore inherits the
  parent's tables unless the fighter file overrides them.

### 4.2 Observed cases

- **Falco** (`src/Character.asm:3677`): parent FOX, `add_actions = 0`. Reuses Fox's action slots 0xE1/0xE2 (`Laser`/`LaserAir`,
  `src/Action.asm:725-726`) and overwrites the entries with the Phantasm ones (`src/Falco/Falco.asm:101-102`; constants at `:156-157`).
  The moveset is his own (`src/Falco/moveset/*.bin`, `:2-53`). It does **not** go through `foxshared.asm`: that file only patches the
  `recovery_logic` and `cpu_post_process` tables for FOX and JFOX (`src/foxshared.asm:129, 131, 180, 182`).
- **NFalco** (`src/NFalco/NFalco.asm`): parent FOX (`src/Character.asm:3793`). Uses the moveset labels of `Falco.*` (for example
  `Falco.RUN` at `NFalco.asm:14`), so it reuses Falco's code by label reference. Defines `menu_zoom` (`NFalco.asm:74`), `ai_attack_prevent`
  (`:79`), `action_string` (`:85`) and calls `polygon_setup(NFALCO, FALCO)` (`:90`).
- **Marth** (`src/Marth/Marth.asm`): parent CAPTAIN (`src/Character.asm:3735`), 8 new actions (`add_actions = 8`). New actions with
  `Character.add_new_action(MARTH, ...)` (`src/Marth/Marth.asm:462-465`); `air_nsp` id table (`:467`). Uses `Moveset.shared.*`
  (`src/Moveset.asm:288`, scope `shared`) and `Kirby.Action` constants (13 occurrences). Roy (`src/Roy`) references Marth.
- **Sonic** (`src/Sonic/Sonic.asm`): parent FOX (`src/Character.asm:3737`), 18 new actions (`add_actions = 18`). New actions with
  `add_new_action` (`src/Sonic/Sonic.asm:317-321`) and `SonicDSP.*` subroutines. Uses `Sonic.classic_table` (3 occurrences) and
  `Kirby.Action` (24 occurrences).

### 4.3 How shared code is parameterised

- The `*shared.asm` files (`linkshared`, `captainshared`, `dkshared`, `nessshared`, `jigglypuffkirbyshared`, `yoshishared`, `pikashared`,
  `samusshared`, `marioshared`, `foxshared`) are included globally from `main.asm:136-146`. Each only edits the id tables of the fighters it
  cares about. Example: `jigglypuffkirbyshared.asm:1027-1031` (recovery_logic of JIGGLYPUFF, JPUFF, EPUFF).
- For an action of a common moveset (for example a parent's command), `Character.add_concurrent_commands(name, action, command)`
  (`src/Character.asm:433-462`) creates a new version of the command that calls the original with `CONCURRENT_STREAM`, leaving the original alone.
- To test for a polygon in code the Remix compares with `NUM_CHARACTERS - NUM_POLYGONS` (for example `src/AI.asm:2513`), so the polygons
  must occupy the end of the id range contiguously (`0x4D-0x60`).

## 5. Hooks: vanilla code sites that read the tables

Source: `origin` + `base` and `OS.patch_start(ROM, RAM)` in `src/Character.asm` and `src/Costumes.asm`. The decomp name is the last
`// 0x8XXXXXXX` comment before the position; `+0xNN` is the distance from the start of that function. A large offset (above 0x100) means the
annotated function may not be the one that holds the hook. Rows marked "overlay" sit in `0x8010xxxx` to `0x8013xxxx`, where several overlays
share the address, and name the overlay that owns the Remix patch; the full per-patch resolution is `tools/audit_remix_patches.py`.

The five most critical for boot and spawn:

1. `assign_segments_`: ROM `0x5284C`, RAM `0x800D704C`, changes the `s7` limit to `NUM_CHARACTERS` (`src/Character.asm:1171-1176`). Decomp: `ftManagerSetupFileSize+0x6C` (`decomp/src/ft/ftmanager.c`).

4. `move_action_array_table_`: ROM `0x62BD0`, RAM `0x800E73D0`, reads the action array pointer from `ACTION_ARRAY_TABLE` with a carry on the upper half (`src/Character.asm:1207-1219`). Decomp: `ftMainSetStatus+0x4AC` (`decomp/src/ft/ftmain.c`).

### 5.1 Reading notes

- The `0x8010xxxx` to `0x8013xxxx` range holds overlays (for example `ftComputer` code, the CSS and results menus). The `select_`,

## 6. How the port implements it

| Remix mechanism | Port implementation |
|---|---|
| Fighter ids 0x00 to 0x60 | The Remix id is the port fkind: `REMIX_ID_TO_PORT_FKIND(id) = id` (`port/remix/remix_roster_data.h`). 0x00 to 0x1A are the vanilla fkinds. 0x1B (RANDOM) is registered because the VS character select shows its "?" model; it is never fought. 0x1C stays unregistered so fkind 28 (`nFTKindNull`) never names a fighter. 0x1D to 0x60 are the Remix fighters. |
| Roster facts of `define_character` (name, parent, `add_actions`, costume counts, `variant_type`, `sound_type`, polygon flag, files, `attrib_offset`, `menu_zoom`) | `kRemixRoster[97]` in `port/remix/remix_roster_data.h`, generated from `src/Character.asm` and `src/costumes/*.asm` by `tools/gen_remix_roster.py` (see `docs/remix/roster_data.md`). |
| Struct table (`FTData` per fighter) | Torch writes the table to the o2r as `remix/fighters` (`SSB64:REMIXFIGHTERS`, `docs/remix/torch_factories.md`); `remix_roster_load()` builds one synth `FTData` per fighter (`docs/remix/roster_loader.md`). |
| Per-id tables (`move_table*`, `id_table*`, 2.2 and 2.3) | `FighterDescriptor` fields in `port/fighter_registry.h`, filled from the parent's row and then overridden with the Remix values; the decomp reads them through `port_fighter_*` accessors. |
| Action arrays and the ids >= 0xDC | `port/remix/remix_action_layout.h` (table addresses and per-id action counts, from `tools/gen_remix_actions.py`) and `ftRemixBindSpecials` (`decomp/src/ft/ftremix/ftremixbind.c`), which fills the special statuses of the descriptor from the Remix action array. The routines themselves are ported per fighter in `decomp/src/ft/ftremix/<fighter>/`. |
| `variant_type`, polygon test `id >= NUM_CHARACTERS - NUM_POLYGONS` | Roster flags (`is_polygon`, `variant_type`) in `kRemixRoster`. |
| Relocated vanilla rows (`o_attributes` of fkinds 13 to 25, `menu_zoom` of 12 to 26, Kirby's copy-ability motions and actions) | Patched at load time by `remix_roster_load()` (`patchVanillaAttributeOffsets`, `patchVanillaMenuZoom`, `bindKirbyCopyActions`). |
| Entry statuses (`Character.entry_action.table`) | Read from the Remix RAM image (`remix/ram_image`, `port/remix/remix_ram_image.h`) at `REMIX_SYM_Character__entry_action__table` (`bindEntryStatuses`). |
| Hooks of section 5 | PORT-gated code in the decomp function that holds the hook (`REGION_REMIX`), reading the descriptor; for example `ftManagerInitFighter`, `ftMainSetStatus`, `ftCommonAttack100StartSetStatus`. |

### Registry

`port/fighter_registry.{h,cpp}` is the single redirection point for per-fkind dispatch. The decomp tables sized by `nFTKindEnumCount`
(27) cannot hold the 97 Remix ids, so each per-fkind dispatch site in the decomp reads a `port_fighter_*` accessor instead of indexing
the array. Rows live in a vector, so there is no fixed capacity: `port_fighter_register(fkind, descriptor)` grows it, and
`port_fighter_kind_limit()` returns one past the highest registered fkind. `port_fighter_seed_vanilla()` (`decomp/src/ft/ftport.c`)
seeds fkinds 0 to 26 from the decomp arrays at boot; `remix_roster_load()` then registers the Remix fighters (`port/port.cpp`).
`port_fighter_parent_fkind(fkind)` returns the vanilla fkind whose tables a fighter reads (the fkind itself for vanilla and unregistered
ones).

Code that needs the vanilla fkind of a synth fighter (for example the Kirby copy tables in `efmanager.c` and `ftcommoncapturekirby.c`)
calls `port_fighter_parent_fkind`; new code that indexes a per-fkind decomp array directly must go through it or an accessor.

### Synth fighter construction

- `FTData`: `port_fighter_synth_ft_create` (`decomp/src/ft/ftport.c`) clones the parent's `FTData` and overwrites the nine file ids,
  `file_main_size`, `o_attributes`, `file_anim_size` and the main-motion and sub-motion arrays from the blob. Runtime slots (`p_file_*`,
  `p_particle`, submotion count) are the synth's own. Particle scripts and textures stay the parent's.
- `FighterDescriptor`: a copy of the parent's, with `ft_data`, `scale` (from `menu_zoom`), `results_name` and the results layout, the
  special statuses and entry statuses of the Remix fighter, and the descriptor hooks of `ftremixdeschooks.c` (ECB override, shield hitlag
  skip) replaced.
