# Smash Remix patch audit: GAP and STUB ledger

Every `OS.patch_start` of the Remix 2.0.1 source (2007), the 80 direct `origin` writes and the 988
`Character.table_patch_start` entries were compared with the port (2026-11-05). This file lists what the port is missing or
only half does, one ID per item; [`patch_audit_scopes.md`](patch_audit_scopes.md) has the verdict and the port location of
every scope (the asm-to-C map). The plan that schedules these items is `ROADMAP.md`, M11 Phase 5b (AI items: Phase 6).

How it was produced:

1. `.toolchain/host/venv/bin/python -I tools/audit_remix_patches.py --out <file>.tsv` lists each patch with the decomp function
   at its RAM address (overlays are told apart by matching function prologues against the vanilla ROM; the ROM is only read)
   and whether that function names a Remix symbol (`hooked`). The flag is a hint, not a verdict.
2. Each scope was then read in the asm and compared with the port by hand, in ten groups (the prefixes below).

Verdicts:

| Verdict | Meaning |
|---|---|
| PORTED | the port reproduces the behaviour |
| ADAPTED | same visible behaviour through another mechanism (ImGui menu, CVar, data read) |
| STUB | a hook exists but skips the behaviour (early return, invented value) |
| GAP | the behaviour is missing |
| NA | not needed on PC, with the reason checked in the asm (N64 memory, boot, debug-only, unreachable code) |

Item states: `open`, `done (<commit or test>)`, `n/a (<reason checked in the asm>)`. Effort: S a few lines, M a helper and
several sites, L a subsystem. Line numbers are those of the audit date; search the symbol if they moved. Inside a group,
"#n", "item n" and "gap n" mean the ID `<prefix>-n` of that group, and "g1" to "g10" name the groups in this order: OP, MN, ST, IT,
GP, SH, FT, MD, MS, CT.
